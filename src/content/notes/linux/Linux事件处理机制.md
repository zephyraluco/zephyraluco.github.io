## 第一代多路复用：select

`select` 是最早的 I/O 多路复用机制（POSIX 标准）：应用把一组 FD 交给内核监控，内核返回后再处理就绪 FD

### 工作原理与缺点

1. **硬上限限制**：`select` 使用一个位图（Bitmap）来存储关注的 FD，在 Linux 中这个大小通常被硬编码为 **1024**（即 `FD_SETSIZE`）。这意味着单个进程最多只能同时监控 1024 个 Socket
2. **双向内存拷贝**：每次调用都要在用户态和内核态之间拷贝整组 FD
3. **O(n) 扫描**：返回后仍需遍历全部 FD 才能找到活跃连接

## 现代工业顶梁柱：epoll

为解决 `select/poll` 的瓶颈，Linux 2.6 引入了 `epoll`，它也是多数高性能网络框架的基础

### 核心机制

- **红黑树（监控集合）**：通过 `epoll_ctl` 维护 FD，增删改代价低（$O(\log n)$），无需每次全量拷贝
- **就绪队列**：活跃 FD 会进入 `ready_list`
- **事件返回**：`epoll_wait` 直接返回就绪 FD，处理路径接近 $O(1)$

### 工作模式：LT vs ET

- **水平触发（LT，默认）**：缓冲区有未读数据就会持续通知
- **边缘触发（ET）**：状态变化时通知一次；必须循环读取到 `EAGAIN`，否则可能漏处理

### epoll 的局限

`epoll` 仍有两个典型开销：

1. **系统调用开销**：`epoll_wait` 需要频繁用户态/内核态切换
2. **仍是同步 I/O**：只负责通知，真正数据读写仍由应用发起

## 异步 I/O：io_uring

Linux 5.1 引入 `io_uring`，目标是进一步降低系统调用与上下文切换开销，实现更完整的异步 I/O

### 工作原理

`io_uring` 在用户态和内核态之间共享内存，核心是两个环形队列：

1. **提交队列（SQ）**：应用提交请求（SQE）
2. **完成队列（CQ）**：内核完成后回填结果（CQE）

### 为什么 io_uring 更快？

- **更少系统调用**：在 `SQPOLL` 等模式下，可显著减少 syscall 次数
- **提交与完成解耦**：应用提交后可继续执行，完成结果异步回收
- **统一接口**：可同时覆盖网络 I/O、文件 I/O 等场景

## 综合对比总结

| 特性                  | select                   | epoll                             | io_uring                                |
| :-------------------- | :----------------------- | :-------------------------------- | :-------------------------------------- |
| **I/O 模型**          | 同步多路复用             | 同步多路复用                      | **真正异步 I/O**                        |
| **连接数限制**        | 有（通常 1024）          | 无限制（取决于内存）              | 无限制（取决于内存）                    |
| **数据结构**          | 线性数组（Bitmap）       | **红黑树 + 就绪链表**             | **双环形队列（Ring Buffer）**           |
| **时间复杂度**        | $O(n)$ （需要全量遍历）  | $O(1)$ （只处理就绪连接）         | $O(1)$ （直接内存交互）                 |
| **用户态/内核态拷贝** | 每次调用都要双向全量拷贝 | 仅在增删改时拷贝（`epoll_ctl`）   | **通过共享内存，实现零拷贝**            |
| **支持的 FD 类型**    | 网络 Socket、管道        | 网络 Socket、管道                 | **网络 Socket、磁盘文件、全部通用**     |
| **系统调用频率**      | 极高                     | 高（每次等待都需要 `epoll_wait`） | **极低，甚至可以通过内核轮询做到 0 次** |
